# GUI QA tooling for the agent: research note

Research note outside the website-projected documentation (English-only by decision; i18n can be added later). Question: which products and tools let an AI coding agent **directly interact with and view** a locally running web app — here, the DSH web GUI served by `dsh web` at `http://127.0.0.1:3080` — for hands-on visual and functional QA? Written August 2026; every maintenance claim was checked against the live repo/npm/registry state in the same month. All claims cite primary sources (official docs, GitHub repos, first-party APIs); secondary commentary is avoided.

Environment facts this note is written against:

- The GUI is a React bundle served on loopback with persistent streaming channels (`ws://localhost:3080/api/events.mux`, `/api/events.host` are wired in `packages/client/connection`), so "the network never goes idle" is structural, not incidental.
- Playwright 1.61.1 is already in the workspace (`node_modules/playwright`), Chrome is installed on the host, and ffmpeg is available.
- The repo already has a browser e2e lane (`apps/web/tests`, run via `pnpm run test:web`) that boots the real composition and drives real Chromium over HTTP, with aria-golden snapshots (`captureStableAria`) and browser-locale control ([lane README](../../apps/web/tests/README.md)).
- `.playwright-mcp/` is gitignored at the repo root, and the [record-browser-gif](../../.agents/skills/record-browser-gif/SKILL.md) skill already assumes a browser-control skill plus a browser-tool screenshot output directory.
- A separate session skill uses Chrome DevTools MCP for performance analysis.

## 1. Executive summary

Ranked for THIS environment (agent with shell access on macOS arm64, Node 22+, pnpm workspaces, localhost-only GUI):

1. **Playwright CLI + skills (`@playwright/cli`)** — Microsoft's own guidance routes coding agents with shell access to the CLI+SKILLS workflow over MCP because CLI invocations avoid loading large tool schemas and verbose accessibility trees into model context ([README comparison](https://github.com/microsoft/playwright-cli)); it keeps a persistent session, writes snapshots/screenshots under `.playwright-cli/` (same pattern as our gitignored `.playwright-mcp/`), exposes `console`, `requests`, tracing, video, and a live `show` dashboard — the closest thing to a two-way visual feedback loop that runs entirely locally and deterministically.
2. **Playwright MCP (`@playwright/mcp`)** — the same engine as MCP tools when an MCP client surface is preferable; snapshot-first interaction (`browser_snapshot`) plus opt-in `--caps=vision,pdf,devtools,network,storage,testing` capability groups ([capabilities doc](https://playwright.dev/mcp/capabilities)), Apache-2.0, very active (~36k stars).
3. **Chrome DevTools MCP (`chrome-devtools-mcp`)** — Google's official DevTools-for-agents server: console/network/performance-trace/Lighthouse tooling over puppeteer with source-mapped stack traces, attaches to real running Chrome via `--browser-url` or `--autoConnect`; complements (not replaces) Playwright MCP for performance work ([README](https://github.com/ChromeDevTools/chrome-devtools-mcp)).
4. **Playwright built-ins: trace viewer + `toHaveScreenshot` + codegen** — already installed at 1.61.1; traces give per-action DOM snapshots + console + network replay ([trace viewer docs](https://playwright.dev/docs/trace-viewer)), `toHaveScreenshot` gives a fully local visual-regression gate with animation disabling by default ([visual comparisons docs](https://playwright.dev/docs/test-snapshots)). No new dependency for gates (b) and (c) of §8.
5. **axe-core via `@axe-core/playwright` / `@axe-core/cli`** — machine-readable accessibility violations per page, headless-friendly, exit-code-gateable ([axe-core-cli README](https://github.com/dequelabs/axe-core-npm/blob/develop/packages/cli/README.md)); cheap to bolt onto both interactive QA and CI.
6. **Stagehand** — if natural-language actions inside Node tests ever become desirable: `act()`/`extract()`/`observe()` over a CDP-native runtime, self-hostable against local Chromium, with an explicit determinism path (`observe()` returns `Action`s that replay "with no inference at all"); uncached natural-language actions still cost inference per call ([stagehand docs](https://docs.stagehand.dev/v4/basics/act)).
7. **Cloud agentic-QA SaaS (Checkly, QA Wolf, Momentic, mabl, Reflect, TestIM, Hercules)** — several now ship genuine local-execution modes (Momentic `npx momentic run`, mabl `mabl tests run` at zero credits, QA Wolf's 2026 CLI), but every one binds results to vendor accounts and layers an LLM-authored test format over a stack that already runs Playwright natively; pure-cloud runners (Reflect, TestIM grids, Browserbase) cannot reach `127.0.0.1:3080` at all without tunneling ([§5](#5-functional-test-generation--agentic-qa-services)).
8. **SaaS visual-regression platforms (Percy, Chromatic, Applitools)** — only worth revisiting if DSH grows a hosted deployment with public URLs; for a localhost GUI their cloud-baseline model buys little over local `toHaveScreenshot` baselines.

The one-line conclusion: **stay in the Playwright family** — CLI/skills for the interactive loop, MCP servers where an MCP surface helps, `toHaveScreenshot` + traces for gates, axe for conformance — and treat everything cloud-side as out of scope until DSH ships a publicly reachable URL.

## 2. MCP browser servers

### 2.1 Playwright MCP (`microsoft/playwright-mcp`)

**Status:** actively maintained by Microsoft; ~36.4k stars, license Apache-2.0, repo pushed 2026-08-21, not archived (GitHub API metadata checked 2026-08). Distributed as `@playwright/mcp`, latest stable v0.0.79 (August 2026) on a monthly cadence plus daily alpha builds ([npm registry](https://registry.npmjs.org/@playwright/mcp/latest)); the server implementation lives inside the Playwright monorepo ([microsoft/playwright](https://github.com/microsoft/playwright)), with `microsoft/playwright-mcp` kept as the public entry point.

**Positioning.** An MCP server providing browser automation using Playwright, enabling LLMs to interact with pages "through structured accessibility snapshots, bypassing the need for screenshots or visually-tuned models"; key features listed as fast/lightweight (accessibility tree, not pixel-based input), LLM-friendly (no vision models needed), deterministic tool application ([README](https://github.com/microsoft/playwright-mcp)).

**Primitives (exact tool names from the generated README tool table).** Core automation group includes: `browser_close`, `browser_console_messages` (params `level`, `all`, `filename`), `browser_drag`, `browser_drop`, `browser_evaluate`, `browser_fill_form`, `browser_find` ("search the snapshot for text, returns matching nodes"), `browser_handle_dialog`, `browser_hover`, `browser_navigate`, `browser_navigate_back`, `browser_network_requests`, `browser_press_key`, `browser_click`, `browser_resize`, `browser_run_code_unsafe` ("run Playwright code"), `browser_select_option`, `browser_snapshot` ("Capture accessibility snapshot of the current page, this is better than screenshot", with optional `target`, `filename`, `depth`, `boxes` bounding-box coordinates), `browser_take_screenshot` ("You can't perform actions based on the screenshot, use browser_snapshot for actions"; params include `type`, `filename`, `fullPage`, `scale`), `browser_tabs`, `browser_type`, `browser_wait_for` ([README Tools section](https://github.com/microsoft/playwright-mcp#tools)).

**Capability groups beyond core**, enabled via `--caps=vision,pdf,devtools` (env `PLAYWRIGHT_MCP_CAPS`) or config-file `capabilities`: vision adds coordinate-based mouse tools `browser_mouse_move_xy`, `browser_mouse_click_xy`, `browser_mouse_drag_xy`, `browser_mouse_down`, `browser_mouse_up`, `browser_mouse_wheel`; devtools adds `browser_annotate` ("Open the Playwright Dashboard in annotation mode… Returns the annotated screenshot, ARIA snapshot, and the list of annotations"), `browser_highlight` / `browser_hide_highlight`, `browser_resume` (resume paused script execution with step-by-step debugging), `browser_start_tracing` / tracing stop, `browser_start_video` / video stop; pdf adds `browser_pdf_save`; testing adds assertions `browser_generate_locator`, `browser_verify_element_visible`, `browser_verify_list_visible`, `browser_verify_text_visible`, `browser_verify_value`; further groups exist for network, storage, and config introspection (`browser_get_config`) ([capabilities page](https://playwright.dev/mcp/capabilities); [README devtools/testing groups](https://github.com/microsoft/playwright-mcp#tools)).

**Visual feedback vs snapshots.** Both planes, deliberately asymmetric: interaction targets come from the accessibility snapshot (refs like `e12`), while `browser_take_screenshot` returns real image content to clients that accept images — downscaled to roughly ≤1568px/1.15MP, the image limits of Claude-style clients — unless a `filename` is given, and every action response carries an automatic fresh accessibility snapshot ([config file schema in README](https://github.com/microsoft/playwright-mcp#configuration-file); [README Tools section](https://github.com/microsoft/playwright-mcp#tools)). The README explicitly steers *actions* through snapshots ("You can't perform actions based on the screenshot").

**Streaming apps / networkidle — verified at source level.** The server's navigation path never touches networkidle: `browser_navigate` calls `page.goto` with `waitUntil: 'domcontentloaded'` and then a capped `waitForLoadState('load', { timeout: 5000 })` in the Playwright monorepo's MCP tool source (`playwright-core/src/tools` there, navigation implementation), so an SSE/WebSocket app cannot hang its navigation ([microsoft/playwright-mcp](https://github.com/microsoft/playwright-mcp)). This matches upstream policy: the API docs mark `'networkidle'` as **DISCOURAGED** — "Don't use this method for testing, rely on web assertions to assess readiness instead" ([Page.goto docs](https://playwright.dev/docs/api/class-page)) — and maintainers state "We don't plan on extending the support for `networkidle`. Playwrights actions and assertions will retry until the condition is met - so there is never a need for `networkidle`." ([comment on issue #36730](https://github.com/microsoft/playwright/issues/36730)). Two nuances matter for a WS/SSE app: Playwright patched networkidle to ignore open EventSource connections (spec test "should not wait for an open EventSource connection", tracked as [#37226](https://github.com/microsoft/playwright/issues/37226)), but WebSocket connections still block networkidle per issue discussion ([#37080](https://github.com/microsoft/playwright/issues/37080) reports networkidle "may hang forever if there are persistent requests"). Additionally the MCP config exposes `timeouts.settle` — "How long to wait after each action for triggered work (navigations, requests) to settle before responding. Defaults to 500ms" — which is the knob for giving streamed UI updates time to land after a click ([config schema](https://github.com/microsoft/playwright-mcp#configuration-file)). Net effect: the SSE-hang failure mode of hand-rolled scripts does not arise from the MCP's own navigation waits.

**Install/config surface.** Claude-style JSON config: `{"mcpServers": {"playwright": {"command": "npx", "args": ["@playwright/mcp@latest"]}}}`; for Claude Code, `claude mcp add playwright npx @playwright/mcp@latest` ([README getting started](https://github.com/microsoft/playwright-mcp#getting-started)). The browser runs **headed by default** ("Pass `--headless` to disable"), keeps a persistent profile under `ms-playwright/mcp-{channel}-{workspace-hash}` that only one browser instance may use at a time (concurrent clients need `--isolated` or distinct `--user-data-dir`), and can attach to an existing browser via `--cdp-endpoint <endpoint>` or the `--extension` mode ([README user profile and configuration](https://github.com/microsoft/playwright-mcp#user-profile); [getting-started docs](https://playwright.dev/docs/getting-started-mcp)). Screenshots and other output files default to a `.playwright-mcp/` directory under the current working directory (the origin of this repo's gitignored path; overridable via `--output-dir` / env `PLAYWRIGHT_MCP_OUTPUT_DIR`) ([README configuration flags](https://github.com/microsoft/playwright-mcp#configuration)). Config file via `--config` supports `outputDir`, `console.level` filtering, `network.allowedOrigins`/`blockedOrigins` with wildcard-port formats like `http://localhost:*`, `testIdAttribute` ("Specify the attribute to use for test ids, defaults to \"data-testid\""), `timeouts.action/navigation/expect/settle`, `saveSession`, `secrets` response masking, and `remoteEndpoint` for connecting to a remote Playwright endpoint ([config schema](https://github.com/microsoft/playwright-mcp#configuration-file)).

**Microsoft's own routing advice.** The README opens with "Playwright MCP vs Playwright CLI": coding agents should consider [CLI+SKILLS](https://github.com/microsoft/playwright-cli) because "CLI invocations are more token-efficient: they avoid loading large tool schemas and verbose accessibility trees into the model context", while "MCP remains relevant for specialized agentic loops that benefit from persistent state, rich introspection, and iterative reasoning over page structure" ([README](https://github.com/microsoft/playwright-mcp)). For an agent whose native interface is a shell — exactly the DSH case — that advice favors §2.5.

### 2.2 Chrome DevTools MCP (`ChromeDevTools/chrome-devtools-mcp`)

**Status:** maintained by Google LLC ("Chrome DevTools for coding agents"); npm shows author Google LLC, license Apache-2.0, package created 2025-05-13, latest v1.8.0 released August 2026 on a roughly two-to-four-week cadence; ~49.7k GitHub stars — the most-starred of the MCP browser servers ([npm page](https://www.npmjs.com/package/chrome-devtools-mcp); [repo](https://github.com/ChromeDevTools/chrome-devtools-mcp)).

**Primitives.** The generated tool reference groups ~57 tools: interaction (`click`, `drag`, `fill`, `fill_form`, `hover`, `press_key`, `type_text`, `upload_file`, `click_at`), pages/navigation (`navigate_page`, `list_pages`, `new_page`, `select_page`, `close_page`, `wait_for`), `resize_page`, a single `emulate` tool carrying `cpuThrottlingRate` and named `networkConditions` presets plus viewport/color scheme, Performance (3): `performance_analyze_insight`, `performance_start_trace`, `performance_stop_trace`; plus `lighthouse_audit`; network: `list_network_requests`, `get_network_request`; debugging (8): `evaluate_script`, `get_console_message`, `lighthouse_audit`, `list_console_messages`, `take_screenshot`, `take_snapshot`, `screencast_start`, `screencast_stop`; memory/heap tooling, extension/PWA/WebMCP inspection, and a `--slim` mode exposing three tools ([tool reference](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md); [README](https://github.com/ChromeDevTools/chrome-devtools-mcp)). Two behaviors stand out for agent loops: `take_screenshot` attaches image content to the response **by default** (a `filePath` saves it "instead of attaching"), while `take_snapshot` returns the accessibility tree with uids ("Prefer taking a snapshot over taking a screenshot") — the mirror image of Playwright MCP's default ([tool reference](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md)); and console messages come "with source-mapped stack traces", which matters for a bundled React GUI whose raw stacks are minified ([README](https://github.com/ChromeDevTools/chrome-devtools-mcp)).

**Attaches to real Chrome.** Unlike Playwright MCP (which launches its own isolated browser by default), chrome-devtools-mcp can pilot the user's actual running Chrome: `--browserUrl`/`--browser-url http://127.0.0.1:9222` connects to a debuggable instance, and `--autoConnect` connects automatically to a local browser (Chrome 144+) via the user data dir with remote debugging enabled through `chrome://inspect/#remote-debugging` ([README configuration](https://github.com/ChromeDevTools/chrome-devtools-mcp#configuration)). This is the right fit for the harness's existing `web-perf` skill flow.

**Streaming apps.** Verified at source level: navigation calls puppeteer's `goto` without a `waitUntil` override, and Puppeteer's default is `'load'` — no networkidle in the navigation path ([chrome-devtools-mcp](https://github.com/ChromeDevTools/chrome-devtools-mcp); [Puppeteer docs on default lifecycle](https://pptr.dev/api/puppeteer.pagegoto)). Its headline debugging features (console with mapped stacks, network listing, performance traces) are exactly the observability an SSE/WebSocket-heavy GUI needs, and per-page routing (`pageIdx` parameters) supports concurrent agent sessions against multiple tabs.

**Install/config.** Standard client entry: `{"mcpServers": {"chrome-devtools": {"command": "npx", "args": ["-y", "chrome-devtools-mcp@latest"]}}}`; Gemini CLI: `gemini mcp add chrome-devtools npx chrome-devtools-mcp@latest`; options include `--autoConnect`, `--browser-url`, `--channel`, `--isolated`, `--headless`, `--performanceCrux` ("Set to false to disable sending URLs from performance traces to CrUX API" — relevant privacy note for a local product: leave it off) ([README](https://github.com/ChromeDevTools/chrome-devtools-mcp)).

**License:** Apache-2.0 ([npm](https://www.npmjs.com/package/chrome-devtools-mcp)).

### 2.3 Browserbase MCP

**What it is.** Cloud browser automation for LLMs built on Browserbase sessions and Stagehand. The self-hostable server repo ([browserbase/mcp-server-browserbase](https://github.com/browserbase/mcp-server-browserbase), ~3.4k stars, Apache-2.0) is **archived** (README carries an archive banner; archived July 2026 per GitHub API); the product continues as a hosted Streamable-HTTP endpoint at `https://mcp.browserbase.com/mcp` ([setup docs](https://docs.browserbase.com/integrations/mcp/setup)).

**Surface.** The hosted server exposes exactly six Stagehand natural-language operations — `start`, `end`, `navigate`, `act`, `observe`, `extract` — with no screenshot tool and no accessibility-snapshot tool; visual feedback exists only through Browserbase's own dashboard/live view, not in the tool responses. It requires `BROWSERBASE_API_KEY` (+ project ID, plus a Stagehand model key such as `GEMINI_API_KEY`; default model `google/gemini-2.5-flash-lite`) ([setup docs](https://docs.browserbase.com/integrations/mcp/setup)). Pricing is account/SaaS based (API key required; plan gating appears in flags like "--verified Only for Scale Plan Users"); no prices are stated in the docs.

**Fit for localhost: none.** Sessions execute on Browserbase's cloud infrastructure, so navigating to `127.0.0.1` reaches the cloud VM's loopback, not the developer's machine; reaching the local GUI would require exposing it through a tunnel. No localhost mode appears anywhere in the setup documentation. Excluded from the recommended set on both locality and maintenance grounds.

### 2.4 Puppeteer MCP (reference servers)

The historical `@modelcontextprotocol/server-puppeteer` reference implementation exposed `puppeteer_navigate`, `puppeteer_screenshot` (binary image content by default), `puppeteer_click`, `puppeteer_fill`, `puppeteer_select`, and `puppeteer_evaluate` over CSS selectors, plus `console://logs` and `screenshot://<n>` resources ([archived reference README](https://github.com/modelcontextprotocol/servers-archived/tree/main/src/puppeteer)). The reference-server generation is retired: the monorepo README lists Puppeteer under "Archived" pointing at `servers-archived`, and the npm package is marked deprecated ("Package no longer supported", last publish May 2025) ([npm: @modelcontextprotocol/server-puppeteer](https://www.npmjs.com/package/@modelcontextprotocol/server-puppeteer)). Verdict: do not adopt; both active successors above supersede it in capability and maintenance signals.

### 2.5 Playwright CLI + skills (`microsoft/playwright-cli`) — the shell-native sibling

Not an MCP server, but Microsoft's answer to the same question and the best match for a shell-first agent, so it belongs in this comparison. Install `npm install -g @playwright/cli@latest`, then either install skills (`playwright-cli install --skills`) or let the agent read `playwright-cli --help`; the README's stated rationale is identical to the MCP-vs-CLI passage quoted in §2.1, with CLI favored for coding agents ([README](https://github.com/microsoft/playwright-cli)). Package metadata: `@playwright/cli` published by Microsoft Corporation, license Apache-2.0, current release 0.1.18 with npm provenance attestation (npm registry, checked 2026-08).

Capability highlights that map directly onto this task's pain points:

- **Persistent sessions**: cookies/storage survive between CLI invocations within a session; `-s=<name>` isolates projects; `PLAYWRIGHT_CLI_SESSION` env pins the session ([README sessions](https://github.com/microsoft/playwright-cli#sessions)).
- **Two-way visibility**: `playwright-cli show` opens a dashboard with a session grid of live screencast previews and a full remote-control view ("Click into the viewport to take over mouse and keyboard input") ([README monitoring](https://github.com/microsoft/playwright-cli#monitoring)) — the human can watch the agent drive the GUI live.
- **Snapshot-first interaction, files not tokens**: `snapshot` writes a timestamped YAML under `.playwright-cli/page-*.yml` and returns the path; `snapshot --depth=N` bounds size; `find <text>` greps the snapshot with context lines instead of dumping it ([README snapshots](https://github.com/microsoft/playwright-cli#snapshots)).
- **Observability commands**: `console [min-level]`, `requests` ("list all network requests since loading the page"), `request <index>` details, `tracing-start`/`tracing-stop` (feeds Playwright Trace Viewer), `video-start`/`video-chapter`/`video-show-actions`/`video-stop` ([README devtools commands](https://github.com/microsoft/playwright-cli#devtools)).
- **Escape hatches**: `run-code <code>` executes raw Playwright code; `attach --cdp=chrome` attaches to a running Chrome by channel or CDP URL; `generate-locator <ref>` emits a locator for tests ([README](https://github.com/microsoft/playwright-cli)).
- Screenshots: `screenshot [ref] [--filename=f] [--hires]`; headed mode via `open --headed`.

## 3. AI-native browser automation frameworks

These add LLM inference on top of browser automation — natural-language actions, self-healing selectors, DOM+vision grounding — at the price of token cost and nondeterminism. Maintenance verified against live repos/npm/PyPI on 2026-08-25.

**browser-use** ([repo](https://github.com/browser-use/browser-use), [docs](https://docs.browser-use.com/open-source/quickstart)) — Python library where you describe a task and an `Agent(task=..., llm=...)` executes it ("You describe the task, and it completes it"); models are injected objects (`ChatOpenAI`/`ChatAnthropic`/…), CDP access exists via hooks, and vision grounding is controlled by a `use_vision` flag defaulting to `"auto"` ([agent parameters](https://docs.browser-use.com/open-source/customize/agent/all-parameters)). Runtime cost is structural: the default `agent.run(max_steps=100)` performs at least one LLM round per step ([basics](https://docs.browser-use.com/open-source/customize/agent/basics)). Status: MIT, ~110.5k stars, pushed 2026-08-25, release 0.13.8 (2026-08-16), $17M Felicis seed ([blog](https://browser-use.com/posts/seed-round)). Fit note: Python ≥3.11 only — it would run as a sidecar process in this Node/pnpm monorepo, and its free-form task loop is the opposite of repeatable QA determinism.

**Stagehand** ([stagehand.dev](https://stagehand.dev), [repo](https://github.com/browserbase/stagehand)) — TypeScript SDK positioned as "Playwright was built for testing, Stagehand is built for agents," exposing three primitives: `act()` (execute a natural-language action), `observe()` (see what is actionable), `extract()` (pull structured data) ([README](https://github.com/browserbase/stagehand)). v4 (npm `@browserbasehq/stagehand` 4.0.2, August 2026) drops the Playwright dependency for a CDP-native runtime while keeping Playwright-style APIs (`goto`, `click`, `locator`, `screenshot`) and adds Python/Go SDKs ([introduction docs](https://docs.stagehand.dev/v4/first-steps/introduction)); local Chromium works via `localBrowser.launch()` or `localBrowser.connect({ cdpUrl: "http://127.0.0.1:9222" })` ([browser config](https://docs.stagehand.dev/v4/configuration/browser)). Its determinism story is explicit and two-tiered: "Passing an instruction runs model inference… passing an `Action` [returned by `observe()`] replays it deterministically with no inference at all," with `selfHeal` re-inferring broken selectors and server-side step caching avoiding tokens on cached steps — though "with a local browser… every call runs inference" ([act docs](https://docs.stagehand.dev/v4/basics/act); [caching](https://docs.stagehand.dev/v4/best-practices/caching)). MIT, ~24k stars, active the week of observation; Browserbase raised a $40M Series B in June 2025 ([blog](https://browserbase.com/blog/series-b-and-beyond/)). Best Node-native fit of this group, but still LLM-per-action unless driven through replayed Actions.

**Skyvern** ([repo](https://github.com/Skyvern-AI/skyvern)) — vision-LLM workflow automation explicitly selector-free ("no pre-determined XPaths"), driving from screenshots plus DOM; also ships a Playwright extension SDK with prompt-augmented methods (`page.act(prompt)`, `page.extract(prompt, schema)`, `page.validate(prompt)`, `page.agent.run_task(prompt)`) ([README](https://github.com/Skyvern-AI/skyvern)). Cloud offering plus self-hosted Docker; **AGPL-3.0** (license file verified), Python ≥3.11; active (v1.0.51, 2026-08-24; ~22.8k stars). AGPL makes it a licensing non-starter for embedding in this codebase.

**LaVague** ([repo](https://github.com/lavague-ai/LaVague)) — effectively dormant: last commit 2025-01-21, no GitHub releases ever published, site frozen at 2024-era marketing including its "LaVague QA" Gherkin tooling ([repo](https://github.com/lavague-ai/LaVague)). Architecture was a World Model + Action Engine compiling natural-language instructions to Selenium/Playwright code, with roughly three model calls per action cycle ([FAQ](https://docs.lavague.ai/en/latest/docs/get-started/FAQs/)). Third-party reporting connects the parent company's team to H Company after an acquisition ([French Tech Journal, May 2025](https://www.frenchtechjournal.com/la-machine-29-the-france-ai-radar/)); no first-party wind-down statement exists. Do not adopt.

**Magnitude** — premise corrections matter here: the original repository paths redirect; the live project is [magnitudedev/browser-agent](https://github.com/magnitudedev/browser-agent) ("Open-source, vision-first browser agent", Apache-2.0, ~4.1k stars), and its test format is plain TypeScript `test(title, async (agent) => ...)` functions from `magnitude-test` calling `agent.act`/`agent.check`/`agent.extract` with direct `agent.page` Playwright access — not `.mag` files ([test declaration reference](https://docs.magnitude.run/reference/test-declaration)). A planner/executor split (smart planner model; executor is a small pixel-coordinate model) with plan caching gives partial determinism ([launch discussion](https://news.ycombinator.com/item?id=43796003)). Status: **stalled, not archived** — last commit/release/npm publish all February 2026 (`magnitude-test@0.3.13`), with the founders (YC S25) having shut their hosted product in 2025 and since shipping a different offline-agent product ([@magnitudedev/cli](https://www.npmjs.com/package/@magnitudedev/cli), active August 2026). Interesting design, unreliable maintenance.

**Playwright codegen + Trace Viewer** (the deterministic baseline of this category) — `npx playwright codegen <url>` records actions as code with resilient locators ("prioritizing role, text and test id locators") plus recorded assertions (visibility/text/value) and `--save-storage=auth.json` for authenticated-state reuse ([codegen docs](https://playwright.dev/docs/codegen)). Tracing via `context.tracing.start({ screenshots: true, snapshots: true })` / `tracing.stop({ path: 'trace.zip' })` ([Tracing API](https://playwright.dev/docs/api/class-tracing)) or the runner's `--trace on|retain-on-failure` flag produces a zip that Trace Viewer renders with per-action DOM snapshots, console, network, source, and errors ([trace viewer docs](https://playwright.dev/docs/trace-viewer)); traces open locally via `npx playwright show-trace` or the fully client-side https://trace.playwright.dev ([trace viewer docs](https://playwright.dev/docs/trace-viewer)). Zero LLM calls, fully deterministic, and an agent can both produce and read traces programmatically — which is why this pair, not any AI-native framework, anchors the recommendation in §8.

**Playwright built-ins** ([visual comparisons docs](https://playwright.dev/docs/test-snapshots)) — `await expect(page).toHaveScreenshot()` generates reference screenshots on first execution and compares on subsequent runs; non-image data uses `toMatchSnapshot()`. Baselines live in a `<spec>-snapshots/` directory next to the test file and are meant to be committed to version control; updates go through `npx playwright test --update-snapshots`. Comparison uses the pixelmatch library with per-assertion or global-config thresholds (`maxDiffPixels`, `maxDiffPixelRatio`, `threshold` YIQ tolerance). Two defaults do exactly what our animation pain point needs: `animations: "disabled"` ("stops CSS animations, CSS transitions and Web Animations"; finite ones fast-forwarded to completion, infinite ones canceled to initial state) and `caret: "hide"` — both default-on for this assertion ([PageAssertions docs](https://playwright.dev/docs/api/class-pageassertions)); volatile elements can be masked at capture time via `maskColor`/`stylePath`. Failure screenshots via `use.screenshot: 'only-on-failure'` ([TestOptions](https://playwright.dev/docs/api/class-testoptions)). For an agent: trigger `npx playwright test --reporter=json` and read structured results (env-tunable output paths), accept intentional changes by re-running with `--update-snapshots` ([test reporters](https://playwright.dev/docs/test-reporters)); diffs render as actual/expected/diff images with slider compare in the HTML report and UI Mode. One documented caveat: "Browser rendering can vary based on the host OS… For consistent screenshots, run tests in the same environment where the baseline screenshots were generated" — pin the official Docker image (`mcr.microsoft.com/playwright:v<version>-noble`) when baselines must be portable ([docker docs](https://playwright.dev/docs/docker)). Apache-2.0, ~95k stars, active.

**Percy** — BrowserStack-acquired since July 9, 2020 ([press release](https://www.browserstack.com/press/browserstack-acquires-percy-visual-testing)); SDK workflow captures the DOM in your local test browser and renders it in Percy's infrastructure ("screenshots are not captured within your test suite but within Percy's infrastructure") ([SDK workflow docs](https://www.browserstack.com/docs/percy/integrate/percy-sdk-workflow)), which means localhost apps work — capture is local (`@percy/core` runs a local API server on port 5338) ([npm: @percy/core](https://www.npmjs.com/package/@percy/core)). Pricing model: freemium usage-based on rendered screenshots — "The free plan includes 5,000 free monthly screenshots, unlimited users, and unlimited projects", overage-billed beyond included quotas ([plans and billing](https://www.browserstack.com/docs/percy/overview/plans-and-billing)). CLI packages MIT; actively published ([registry](https://registry.npmjs.org/@percy/cli)).

**Chromatic** — "a cloud service made by the Storybook team" ([Storybook visual testing docs](https://storybook.js.org/docs/writing-tests/visual-testing)), Storybook-first but also integrating Playwright/Cypress; baselines live in Chromatic's cloud keyed by git branch/commit, accepted through its review UI. TurboSnap analyzes git history plus the builder's dependency graph to snapshot only changed stories ([TurboSnap docs](https://www.chromatic.com/docs/turbosnap/)). Strongest programmatic surface of the SaaS group: a fully documented CLI exit-code contract (`0 OK`, `1 BUILD_HAS_CHANGES`, `2 BUILD_HAS_ERRORS`, …, `11 ACCOUNT_QUOTA_REACHED`, `101 GIT_NOT_CLEAN`) ([CLI docs](https://www.chromatic.com/docs/cli/)) plus a public GraphQL API used to query build status and mirror review actions ([schema cataloged from the official endpoint](https://github.com/chromaui/addon-visual-tests)). Pricing model: freemium per-billed-snapshot quotas — "$0/month — 5,000 billed snapshots… Unlimited projects & users" on the free tier ([pricing](https://www.chromatic.com/pricing)). CLI MIT, very active.

**Applitools Eyes** — positions "Visual AI" against naive pixel matching ("automatically ignoring harmless environment noise") ([platform pricing page](https://applitools.com/platform-pricing/)); dedicated `@applitools/eyes-playwright` SDK configured under `eyesConfig` in `playwright.config.ts` ([configuration docs](https://applitools.com/docs/eyes/playwright/api/common-configuration)). Runners split into Classic (local machine) and Ultrafast Grid (cloud cross-browser rendering, separate license) ([runner configuration](https://applitools.com/docs/eyes/playwright/api/runner-configuration)); baselines are managed in the Eyes Test Manager cloud ([baselines concept](https://applitools.com/docs/eyes/getting-started/applitools-workflow/baselines)). Batch results are readable via server REST API (`GET /api/v1/batches/{batchId}` with `X-Eyes-Api-Key`, returning passed/failed/unresolved statistics) ([server API](https://applitools.com/docs/eyes/reference/server-api/batches/list-batch-results)). Pricing model: paid SaaS with checkpoint quotas and a "14-day free trial that [is] fully featured" ([FAQ](https://applitools.com/applitools-faq/)). SDKs actively published.

**Lost Pixel** — sunset: the README banner links an announcement stating "We're sunsetting Lost Pixel" as the team joins Figma ([announcement](https://lost-pixel.com/blog/lost-pixel-team-is-joining-figma), site sitemap lastmod 2026-04-22); repo [lost-pixel/lost-pixel](https://github.com/lost-pixel/lost-pixel) is archived, last release v3.22.0 (November 2024). **BackstopJS** — the older Node scenario tool (`backstop test` / `backstop approve` / `backstop reference`; local baselines under `backstop_data/bitmaps_reference`; JUnit + HTML reports; integrated Docker rendering) ([README](https://github.com/garris/BackstopJS#readme)). ## 6. Console/network/error observability for agents

**Playwright MCP.** Observability is first-class in the core group: `browser_console_messages` returns console messages with a severity floor (`level` param defaulting to "info", each level including more severe ones), an `all` switch for "all console messages since the beginning of the session, not just since the last navigation", and a `filename` sink ([README tool table](https://github.com/microsoft/playwright-mcp#tools)). Network: `browser_network_requests` lists requests since page load (params include a URL-regexp `filter` and a `static` switch for successful static resources), and `browser_network_request` (singular) "Returns full details (headers and body) of a single network request, or a single part if `part` is set" by 1-based index, optionally saving to a file ([README tool table](https://github.com/microsoft/playwright-mcp#tools)). Two gaps worth knowing: the generated tool tables expose **no dedicated page-error tool** — uncaught exceptions are reachable only by bridging raw Playwright's `page.pageErrors()` through `browser_run_code_unsafe` — and the network mocking/tracing tools sit behind the `--caps=network`/`--caps=devtools` groups ([README Tools section](https://github.com/microsoft/playwright-mcp#tools)).

**Chrome DevTools MCP.** The deepest per-item introspection of the set: `list_console_messages` supports paging (`pageIdx`/`pageSize`), `includeStackTraces`, `includePreservedMessages` ("over the last 3 navigations"), type filtering, and service-worker scoping; `get_console_message` fetches by id; `list_network_requests` / `get_network_request` mirror that pattern with request/response bodies returned inline or saved to file ([tool reference](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md)). Console stacks arrive source-mapped — decisive for a bundled React GUI whose raw stacks are minified ([README](https://github.com/ChromeDevTools/chrome-devtools-mcp)). Performance tooling (`performance_start_trace` naming Core Web Vitals LCP/INP/CLS, `performance_analyze_insight`) and an agent-facing `lighthouse_audit` ("Get Lighthouse score and reports for accessibility, SEO, best practices… This excludes performance") round out the surface; emulation goes through one `emulate` tool with `cpuThrottlingRate` and named `networkConditions` presets ([tool reference](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md)). Operational notes for this harness: usage statistics are "enabled by default" with `--no-usage-statistics` as the opt-out (auto-disabled when `CI` is set), and performance traces may send URLs to the CrUX API unless disabled ([README disclaimers](https://github.com/ChromeDevTools/chrome-devtools-mcp#disclaimers)).

**Playwright CLI.** `playwright-cli console [min-level]`, `requests`, and `request <index>` return the same data as plain command output, and `tracing-start`/`tracing-stop` produce a trace file that Trace Viewer renders with dedicated Console and Network tabs filterable per action ([CLI README](https://github.com/microsoft/playwright-cli#devtools); [trace viewer features](https://playwright.dev/docs/trace-viewer#console)).

**Raw Playwright APIs** remain the floor for scripted loops: event surfaces `page.on('console')`, `page.on('pageerror')` ("Emitted when an uncaught exception happens within the page"), and `page.on('requestfailed')` — with the documented caveat that HTTP error statuses like 404 are *successful* responses; only transport failures count as `requestfailed` ([class-page events](https://playwright.dev/docs/api/class-page#page-event-requestfailed)). Since v1.56, buffered accessors suit agent loops without listener wiring: `page.consoleMessages()` and `page.pageErrors()` each "return up to (currently) 200 last" entries with an `all | since-navigation` filter, plus matching clear methods ([class-page#page-console-messages](https://playwright.dev/docs/api/class-page#page-console-messages)). Traces capture all channels per action for post-hoc inspection ([trace viewer](https://playwright.dev/docs/trace-viewer)).

**CDP directly.** Everything above rides the Chrome DevTools Protocol; launching Chrome with `--remote-debugging-port` and enabling `Runtime`, `Page`, and `Network` domains gives the wrapper-free route to `Runtime.consoleAPICalled`, `Runtime.exceptionThrown`, and network events ([DevTools Protocol viewer](https://chromedevtools.github.io/devtools-protocol/)), and Playwright itself speaks it via `browserType.connectOverCDP` ([API docs](https://playwright.dev/docs/api/class-browsertype#browsertype-connectovercdp)). For this harness the practical choice is chrome-devtools-mcp (§2.2) or `playwright-cli attach --cdp=…` (§2.5) rather than speaking CDP by hand.

## 7. Accessibility & UX conformance

All four tool families run headless against a bare URL or a driven page and return machine-readable results; all are actively maintained as of August 2026.

**axe-core** ([repo](https://github.com/dequelabs/axe-core)) — the injectable engine: `axe.run(context, options)` returns a results object split into `passes`, `violations`, `incomplete` ("needs review"), and `inapplicable`, where each violation carries `id`, `impact` ("minor", "moderate", "serious", or "critical"), `help`, `helpUrl`, `tags`, and affected `nodes[]` ([API docs](https://github.com/dequelabs/axe-core/blob/develop/doc/API.md#results-object)). Rule scope is tag-driven (`runOnly: { type: 'tag', values: ['wcag2a'] }`; tags cover `wcag2a…wcag22aa`, `best-practice`, `section508`, `EN-301-549`, and more) ([tags table](https://github.com/dequelabs/axe-core/blob/develop/doc/API.md#axe-core-tags)). MPL-2.0; v4.13.0 released 2026-08-05, active ([releases](https://github.com/dequelabs/axe-core/releases)).

**@axe-core/playwright** — the in-test integration for this repo's lane: `new AxeBuilder({ page }).analyze()` returns the full results object, chainable with `.withTags(['wcag2a','wcag2aa'])`, `.withRules()`, `.disableRules()`, `.include()`/`.exclude()` ([README](https://github.com/dequelabs/axe-core-npm/blob/develop/packages/playwright/README.md)). Library-only: no exit codes — a gate asserts on `results.violations`. Versioned to track the embedded engine (4.13.0, MPL-2.0, released 2026-08-11).

**@axe-core/cli** — the per-page CI gate: `axe http://127.0.0.1:3080 --exit --stdout > axe.json` runs headless Chrome against the URL, writes the full JSON result object to stdout (`--save file.json` / `--dir ./axe-results/` also available), and "exit[s] with a failure code `1` when any rule fails to pass" via `--exit` ([README](https://github.com/dequelabs/axe-core-npm/blob/develop/packages/cli/README.md)); rule selection mirrors the builder (`--tags wcag2a`, `--rules`, `--include/--exclude`). An agent can therefore trigger an audit and read structured violations without any test harness.

**Lighthouse CLI** ([GoogleChrome/lighthouse](https://github.com/GoogleChrome/lighthouse)) — category-scoped audits with JSON output: `lighthouse http://127.0.0.1:3080 --output=json --output-path=./report.json --only-categories=accessibility,best-practices` ("Available categories: accessibility, best-practices, performance, seo"), using locally installed Chrome (`CHROME_PATH`) ([README CLI options](https://github.com/GoogleChrome/lighthouse#cli-options)). Exit codes matter for gating: the CLI exits nonzero only on fatal errors (runtime/connection/protocol-timeout) — score regressions gate through the official companion [lighthouse-ci](https://github.com/GoogleChrome/lighthouse-ci), not the raw CLI ([run.js](https://github.com/GoogleChrome/lighthouse/blob/main/cli/run.js); [README ecosystem](https://github.com/GoogleChrome/lighthouse#lighthouse-ci)). Apache-2.0; v13.4.1 (July 2026) with continuous dev publishes — active. Note chrome-devtools-mcp already embeds this as its `lighthouse_audit` tool (§6).

**IBM Equal Access Toolkit** ([IBMa/equal-access](https://github.com/IBMa/equal-access)) — the `accessibility-checker` npm package works "with test frameworks such as Selenium, Puppeteer, Playwright" and validates against baseline files; the bundled `achecker` CLI scans a URL/file/directory with flags `--ruleArchive`, `--policies` (e.g. `IBM_Accessibility`, `WCAG_2_1` via `.achecker.yml`), `--failLevels`, `--outputFormat json|csv|xlsx|html` ([repo README](https://github.com/IBMa/equal-access#usage); [CLI source](https://github.com/IBMa/equal-access/blob/master/accessibility-checker/src-ts/bin/achecker.js)). Gating is built in: after scanning, nonzero failures set `process.exitCode = 1`, tunable through `--failLevels`. Apache-2.0; releases through 4.0.31 (2026-08-21) — active.

**Static counterpart:** eslint-plugin-jsx-a11y checks JSX statically but, per its own README, only catches static-code errors and should be combined with rendered-DOM testing ([README](https://github.com/jsx-eslint/eslint-plugin-jsx-a11y#eslint-plugin-jsx-a11y)).

For this repo the pragmatic pairing is `@axe-core/playwright` inside the existing lane for gated assertions plus one-shot `axe … --exit --stdout` audits during interactive QA sessions.

## 8. Fit assessment for this harness

**Recommendation by use case.**

**(a) Interactive exploration/QA by the agent:** adopt **Playwright CLI + skills** (`@playwright/cli install --skills`) as the primary loop, matching Microsoft's own routing of shell-first coding agents away from MCP tool schemas ([CLI README](https://github.com/microsoft/playwright-cli)). It gives the agent persistent sessions (`-s=dsh-gui`), file-based snapshots under `.playwright-cli/` that fit the existing gitignored-output-dir pattern, `console`/`requests` observability commands, tracing/video capture, and the `show` dashboard so a human can watch or seize control live ([README monitoring](https://github.com/microsoft/playwright-cli#monitoring)). Keep **Chrome DevTools MCP** mounted as the second opinion for performance analysis and console deep-dives — its `performance_start_trace`/`performance_analyze_insight`, source-mapped console stacks, and `--browser-url` attach-to-running-Chrome mode complement rather than duplicate the Playwright surface ([README](https://github.com/ChromeDevTools/chrome-devtools-mcp)). Playwright MCP remains the right choice only for clients without a shell; this harness always has one.

**(b) Repeatable visual regression gates:** use **Playwright Test's built-in `toHaveScreenshot()`** inside the existing `apps/web/tests` lane — zero new dependencies at the installed version. It generates local baseline files on first run, updates via `--update-snapshots`, disables CSS animations/transitions/Web Animations by default (`animations: "disabled"` is the documented default), supports `maxDiffPixels`/`maxDiffPixelRatio` thresholds globally through `expect.toHaveScreenshot` config, and renders diffs (actual/expected/diff, slider compare) in the HTML report ([visual comparisons docs](https://playwright.dev/docs/test-snapshots)). Baselines live in-repo next to specs, so review happens in PRs exactly like aria goldens do today. SaaS platforms (Percy/Chromatic/Applitools) add cloud baselines and cross-browser grids this single-browser localhost product does not need; revisit only if DSH ships hosted deployments needing visual gating across browsers.

**(c) Functional smoke flows:** keep authoring them in the existing vitest + Playwright lane (`pnpm run test:web`) with `captureStableAria` goldens and pinned browser locale ([lane README](../../apps/web/tests/README.md)); use `playwright-cli generate-locator` or codegen to bootstrap new flows deterministically ([codegen docs](https://playwright.dev/docs/codegen)). Agentic-QA SaaS (§5) adds LLM nondeterminism and account-bound cloud components for no benefit against a loopback target; Hercules-style Gherkin agents cost LLM calls per step and cannot beat scripted determinism for gates.

**Repo changes the recommendation implies.**

- **Test id convention.** The GUI currently ships no `data-testid` attributes (grep over the client sources returns none), and both Playwright surfaces default their test-id attribute to `"data-testid"` ([playwright-mcp config](https://github.com/microsoft/playwright-mcp#configuration-file)). Adding stable test ids to interactive chrome (composer, rail, dialogs) makes locators immune to copy changes and locale drift; if a different attribute name is preferred, both tools accept a custom one (CLI/config `testIdAttribute`).
- **Animation policy for screenshots.** `toHaveScreenshot` covers gated comparisons; any ad-hoc screenshot comparison the agent performs should pass `animations: 'disabled'` explicitly since plain `page.screenshot` does not disable animations ([screenshot option docs](https://playwright.dev/docs/api/class-page#page-screenshot)).
- **Deterministic port handoff.** The e2e scaffold already probes an OS-assigned free port and passes a concrete `--port` to the spawned server because the product requires one ([support.ts](../../apps/web/tests/support.ts)); agent-driven sessions should follow the same probe pattern rather than assuming 3080, or use `dsh web`'s fixed port when no other instance runs.
- **Onboarding gating.** The lane documents that a fresh world boots into workspace-trigger/onboarding view states and handles them with dedicated scenarios and overlays ([onboarding e2e scenarios](../../apps/web/tests/onboarding-deepseek-config.e2e.ts)); ad-hoc agent sessions should reuse that knowledge — either drive onboarding once under `--persistent` (Playwright CLI) / persistent profile (MCP) so later sessions start past it, or seed storage state via `playwright-cli state-load` ([README storage commands](https://github.com/microsoft/playwright-cli#storage)).

**Pain-point mapping.**

- **SSE/streaming vs networkidle:** never introduce `networkidle`; upstream marks it DISCOURAGED and maintainers decline to extend it because web-first assertions retry until satisfied ([Page.goto](https://playwright.dev/docs/api/class-page); [issue #36730 maintainer response](https://github.com/microsoft/playwright/issues/36730)). Both recommended MCP servers provably avoid it in their navigation paths (§2.1, §2.2). For streamed UI updates after actions, raise `timeouts.settle` (default 500ms) or use `browser_wait_for`/`expect(locator).toBeVisible()`. WebSocket connections still block networkidle where someone might reintroduce it ([#37080](https://github.com/microsoft/playwright/issues/37080)); the GUI's persistent `/api/events.mux` channel makes that a permanent hazard.
- **Overlay masks intercepting pointer events:** accessibility-tree interaction converts invisible blockers into explicit tree nodes — a full-screen mask appears as a dialog/presentation element the agent can see, close deliberately, or route around with keyboard tools (`press_key`, `browser_press_key`), which is precisely the fallback the pain point describes. Coordinate-based vision tools exist (`browser_mouse_click_xy`, `click_at`) but are last-resort for masks.
- **First-run onboarding dialogs:** persistent profiles plus seeded storage state (above), mirroring how the lane's onboarding scenarios already gate the flows.
- **Locale drift between source labels and built bundles:** pin the browser locale per session (`locale: 'en-US'` / `zh-CN` as the lane already does — the client derives its initial locale from the browser when no stored preference exists, [support.ts](../../apps/web/tests/support.ts)), assert against roles/test ids instead of copy where possible, and treat localized-label mismatches as expected divergence handled by goldens rather than by selector failure.
